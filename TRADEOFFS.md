# Компромиссы и следующий шаг

## Что сознательно упрощено

- Демо-адаптер хранит изменения в памяти процесса. Он нужен для быстрой проверки без инфраструктуры, но production запускается с PostgreSQL.
- Полнотекстовый поиск пока использует регистронезависимую подстроку после выборки. При росте очереди следует перенести фильтрацию и пагинацию полностью в SQL и добавить `pg_trgm`/FTS.
- RBAC представлен четырьмя фиксированными ролями. Если появятся кастомные роли, правила стоит преобразовать в разрешения и хранить назначения отдельно.
- Уведомления доставляются внутри приложения. Email/webhook требуют outbox-таблицу и отдельного worker, чтобы сетевой сбой не откатывал основную транзакцию.
- Локальные вложения подходят одному инстансу. Для нескольких узлов нужен object storage, антивирусная очередь и подписанные URL.
- SLA считается в календарных минутах. Производственный календарь, часовые пояса клиентов и часы поддержки потребуют отдельного календарного домена.

## Почему не добавлены лишние зависимости

Переходы, RBAC и optimistic locking реализованы маленькими чистыми функциями: это облегчает аудит и не привязывает ядро к framework. Drizzle описывает схему, а SQL выполняется через лёгкий `postgres`-драйвер — так миграции видны явно и сложные транзакции не скрыты ORM.

## Приоритет развития

1. Outbox + worker для гарантированной доставки уведомлений.
2. S3-совместимое хранилище и сканирование вложений.
3. SQL-поиск, курсорная пагинация и индексы по реальному профилю запросов.
4. Метрики OpenTelemetry: latency/error rate API, просрочки SLA, длина очереди.
5. Аудит-лог действий администратора и политика хранения персональных данных.
