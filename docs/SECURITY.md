# Безопасность

## Реализовано

- Сессия содержит 256-битный случайный токен в `HttpOnly`, `SameSite=Lax`, `Secure` production-cookie; в БД хранится SHA-256 хэш с серверным секретом.
- Пароли PostgreSQL-пользователей хэшируются bcrypt с cost 12. Ответ входа не раскрывает, существует ли email.
- Любой защищённый endpoint проверяет сессию и роль на сервере; Client ограничен своим customer, Agent — назначенными заявками.
- Изменяющие browser-запросы с чужим `Origin` отклоняются. CSP, HSTS, frame/referrer/permissions и MIME-sniffing headers выставляются централизованно.
- Zod ограничивает типы и длины входных данных; SQL выполняется только параметризованными tagged templates.
- Пять неудачных входов с одного адреса блокируют попытки на 15 минут. В распределённой production-среде этот счётчик следует перенести в Redis/edge gateway.
- Вложения имеют allowlist MIME, лимиты размера/количества, случайные идентификаторы и защищённую выдачу; имя не участвует в пути хранения.
- Optimistic locking и транзакции предотвращают тихую потерю параллельных изменений.
- Production-аудит зависимостей выполняется командой `npm audit --omit=dev --audit-level=high` в CI.

## Эксплуатационные требования

- Сменить demo-пароли или не загружать seed; использовать секрет длиной 32+ символа.
- Завершать TLS на ingress/reverse proxy, сохранять исходный `Host` и ограничить доверенные proxy.
- Выдать пользователю БД минимальные права, настроить backup/PITR и ротацию credentials.
- Хранить вложения в object storage с malware scanning при работе с недоверенными внешними файлами.
- Не логировать cookie, пароли, содержимое файлов и персональные данные.

Сообщения об уязвимостях не следует публиковать в открытом issue вместе с эксплуатационными деталями; передайте их владельцу проекта приватным каналом.
